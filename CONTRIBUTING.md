# Contributing to RaMiCo

Thank you for helping. Bug reports, questions and pull requests are welcome on
[GitHub](https://github.com/ClaudioDaka99/RaMiCo/issues).

## Setting up

```bash
git clone https://github.com/ClaudioDaka99/RaMiCo
cd RaMiCo
python -m venv .venv            # Python 3.11 to 3.13
.venv/bin/pip install -e ".[dev,tutorials,docs]"   # .venv\Scripts\pip on Windows
pre-commit install
```

The pre-commit hooks run ruff (lint and format) and mypy, fix whitespace, and refuse commits to `main`, large files
and **any PDF file**: papers and figures stay out of the repository.

## Checks

```bash
ruff check . && ruff format --check .
mypy
pytest --cov=ramico         # fails under 80% coverage
mkdocs build --strict
```

Two kinds of tests guard the behaviour of RaMiCo:

- **golden tests** (`tests/golden/`) compare the outputs of the package with fixtures generated by the original
  implementation on synthetic data, except the summaries of numerical features on mixed data, changed on purpose. A change that alters them changes the method: discuss
  it in an issue first. The fixtures are never regenerated to make a test pass;
- **unit tests** cover the public API, and equivalence tests check that optimisations (such as the vectorised
  records) give exactly the same results as the reference code.

## Tutorials

The notebooks in `examples/` are committed with the outputs of their full run, so that GitHub and the documentation
show them. After changing a tutorial or anything it displays, run it again:

```bash
python tools/run_tutorials.py 01            # full mode, written in place
python tools/run_tutorials.py --quick --out build/notebooks   # the published tutorials in quick mode, as CI does
```

Only tutorials 01 and 02 are published for now: `run_tutorials.py`, CI and the documentation take these two, and any
other notebook of `examples/` runs only when named. The full run of tutorial 02 takes about three hours (30 seeds
on Adult): its results are cached in `examples/cache/` (ignored by git), so a run can be interrupted, resumed, or
executed on a server and its cache copied back. Interactive figures go through `ramico.viz.show`, which adds the static PNG copy GitHub needs.

## Commits and pull requests

- One logical change per commit, with a [Conventional Commits](https://www.conventionalcommits.org/) message
  (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `perf:`, `chore:`...).
- Pull requests target `main`; describe what changes for users and add an entry to `CHANGELOG.md`.
- New code comes with tests, type hints and NumPy-style docstrings.

## Releasing

1. Set the version in `src/ramico/__init__.py` and in `CITATION.cff`, and add `date-released` to `CITATION.cff`.
2. In `CHANGELOG.md`, replace `Unreleased` with the date in the heading of the version.
3. Run the checks above, the tutorials in quick mode and `python -m build`.
4. Optionally, run the Release workflow by hand: it publishes the package on TestPyPI.
5. Tag the commit and push the tag (`git tag v0.1.0`, `git push origin v0.1.0`). The Release workflow checks that
   the tag, the version, the changelog and `CITATION.cff` agree, then publishes the package on PyPI.

The documentation is published on GitHub Pages by the Docs workflow at every push to `main`.
